# StreamMind Core Concepts and Relationships

## 1. Design Principles

### Principle 1: Event-Driven Processing

StreamMind is an event-driven processing system.

Events are the primary unit of data movement and processing. However, not every concept in StreamMind is represented as an Event.

State represents information maintained across processing operations, and Context represents the information available during a processing step.

### Principle 2: Logical and Physical State Separation

State is separated into logical State and physical State.

The Pipeline declares logical State and State access relationships.

Operators declare their State dependencies.

The Runtime maps logical State to physical State implementations and manages State execution semantics.

### Principle 3: AI Uses StreamMind Abstractions

AI and Agent components should access State and runtime capabilities through StreamMind abstractions rather than directly depending on the underlying execution engine.

This allows AI capabilities to remain independent of Flink-specific State implementations.

### Principle 4: Extensibility Through Explicit Extension Points

StreamMind should support extensibility through explicit extension points.

Not every component is required to be pluggable. Core abstractions should remain stable, while integrations and replaceable capabilities may be extended through Plugins.

# 2. Core Concepts

## Event

### Definition

Event is the smallest unit of data representation and processing within StreamMind.

An Event may originate from a data source, be generated by the system, or be produced by processing operations.

### Responsibilities

Event represents the unit of data interaction and transportation within StreamMind.

An Event may be consumed, transformed, enriched, filtered, routed, or used to update State.

### Lifecycle

For a data Event:

```text
Created / Received
    ↓
Processed
    ↓
Transformed / Enriched / Routed
    ↓
Written to Sink or Used by Downstream Processing
    ↓
Processing Complete
```

Checkpointing and recovery belong to Runtime and State management semantics rather than being part of the Event's logical lifecycle.

### Open Questions

- Should system-generated Events, such as AI requests or AI responses, be distinguished from external data Events?
- What Event metadata should be standardized by StreamMind?
- Should Event schemas be registered and versioned centrally?

---

## State

### Definition

State represents information that is true or maintained at a particular point in time.

State may represent the accumulated result of past Events, processing progress, system information, or AI and Agent memory.

### Responsibilities

State represents information maintained across processing operations.

State may represent:

- Aggregated information
- Derived information
- Historical information
- Processing progress
- AI or Agent memory
- System-level information

State is independent from Event. Events may influence State, but State does not necessarily contain Events and Events do not own State.

### Lifecycle

```text
State Created
    ↓
State Updated
    ↓
State Expired / Removed
```

State lifecycle may also include persistence, recovery, migration, or restoration depending on the Runtime and physical implementation.

### Open Questions

- In addition to Flink-managed State, should StreamMind manage its own logical State abstractions?
- How should AI short-term memory and long-term memory map to the State model?
- Which State properties should be part of the logical State definition?
- How should State expiration and retention be represented?

---

## Context

### Definition

Context provides a processing-time view of information relevant to an operation.

Context does not own Event or State. It provides access to relevant information required during processing.

### Responsibilities

Context may provide access to:

- Current Event
- Relevant State
- Processing metadata
- Runtime metadata
- External information
- Enriched information

Context acts as an access boundary rather than an ownership boundary.

### Lifecycle

Context exists for the duration required by a processing operation.

```text
Context Created
    ↓
Relevant Information Attached / Made Available
    ↓
Consumed by Operator
    ↓
Processing Complete
    ↓
Context Disposed
```

The exact lifecycle may differ by Runtime and execution model.

### Open Questions

- How should Context distinguish between current Event data and derived or external information?
- Should AI Context be a specialized form of Context or be built from the same base abstraction?
- How should Context size and lifetime be controlled?
- Which Context information should be serializable?

---

## Operator

### Definition

An Operator is a data or system processing operation within StreamMind.

Operators may act on Event, State, and Context.

StreamMind may distinguish between logical Operators and physical Operators.

### Responsibilities

Operators may:

- Read Events
- Transform Events
- Enrich Events
- Filter Events
- Read State
- Update State
- Produce new Events
- Invoke AI models
- Invoke Agents
- Perform system operations

Operators should explicitly declare their dependencies, including required State.

### Logical Operator

Logical Operators define processing behavior.

Examples include:

- Transformation
- Validation
- Enrichment
- Feature calculation
- AI inference
- Agent invocation

### Physical Operator

Physical Operators perform system or execution-related operations.

Examples may include:

- Starting or stopping jobs
- Cleaning resources
- Managing execution-related actions

The exact distinction between logical and physical Operators remains subject to further design.

### Open Questions

- Should all system operations be modeled as Operators?
- What is the exact boundary between logical Operators and physical Operators?
- How should Operator capabilities and dependencies be declared?
- Which Operator abstractions should map directly to Flink Operators?

---

## Pipeline

### Definition

A Pipeline defines a logical processing workflow.

A Pipeline organizes Operators, State definitions, and processing relationships.

The Pipeline itself does not directly process Events. Processing is performed by Operators.

### Responsibilities

A Pipeline defines:

- Participating Operators
- Logical processing topology
- Processing dependencies
- State definitions
- State access relationships
- Logical processing constraints

A Pipeline may represent a linear flow:

```text
A → B → C
```

or a branching topology:

```text
       ┌── B ──┐
A ─────┤       ├── D
       └── C ──┘
```

### Lifecycle

```text
Pipeline Defined
    ↓
Pipeline Validated
    ↓
Pipeline Built / Compiled
    ↓
Pipeline Executed by Runtime
    ↓
Pipeline Stopped / Updated / Removed
```

### Open Questions

- What is the Pipeline API?
- How should Pipeline topology be declared?
- How should Pipeline versioning work?
- How should Pipeline updates interact with existing State?

---

## Runtime

### Definition

Runtime is the execution environment responsible for running StreamMind Pipelines and managing execution semantics.

Runtime does not define what the Pipeline should do. It determines how the Pipeline is executed.

### Responsibilities

Runtime is responsible for:

- Executing Pipelines
- Invoking Operators
- Providing Context
- Mapping logical State to physical State
- Managing physical State
- Determining parallelism
- Determining partitioning
- Scheduling execution
- Managing resources
- Managing checkpointing
- Managing recovery
- Preserving execution semantics

### Lifecycle

```text
Runtime Initialized
    ↓
Pipeline Submitted
    ↓
Execution Planned
    ↓
Pipeline Running
    ↓
Checkpoint / Recovery / Scaling
    ↓
Pipeline Stopped
```

### Open Questions

- How tightly should StreamMind Runtime be coupled to Flink?
- Should multiple Runtime implementations be supported?
- Which execution semantics should be exposed at the StreamMind level?
- Which Runtime details should remain hidden from Pipeline users?

---

## Plugin

### Definition

A Plugin is an extension mechanism for adding or replacing capabilities through explicit extension points.

A Plugin is not necessarily part of the Event processing flow.

### Responsibilities

Plugins may extend:

- Operators
- Runtime capabilities
- State providers
- AI providers
- Agent capabilities
- Sources
- Sinks

Plugin is a cross-cutting extension concept.

The core processing model should not depend on a specific Plugin implementation.

### Lifecycle

```text
Plugin Discovered
    ↓
Plugin Validated
    ↓
Plugin Loaded
    ↓
Plugin Active
    ↓
Plugin Disabled / Unloaded / Replaced
```

### Open Questions

- What is the Plugin API?
- How should Plugin compatibility be managed?
- Which extension points are stable?
- Should Plugins be dynamically loaded at Runtime?

---

## Agent

### Definition

An Agent is an autonomous or semi-autonomous component that can use available capabilities and Context to perform goal-oriented operations.

An Agent is integrated into StreamMind processing through an Operator.

### Responsibilities

An Agent may:

- Consume Context
- Use State through StreamMind abstractions
- Invoke models
- Use tools
- Make decisions
- Trigger downstream actions

### Lifecycle

```text
Agent Invoked
    ↓
Context Provided
    ↓
Reasoning / Planning
    ↓
Tool / Model Invocation
    ↓
Action or Result Produced
    ↓
Agent Execution Complete
```

### Open Questions

- What is the boundary between an Agent and an Agent Operator?
- How should Agent memory map to StreamMind State?
- How should long-running Agent execution interact with streaming workloads?
- Which Agent actions require approval or additional control?

# 3. Core Concept Relationships

## Overview

The current core concepts of StreamMind are:

- Event
- State
- Context
- Operator
- Pipeline
- Runtime
- Plugin
- Agent

These concepts represent different responsibilities within StreamMind.

The purpose of this section is to define how these concepts interact and how StreamMind maps its logical abstractions to the underlying execution engine.

The current conceptual model is:

```text
Event
  │
  │ flows through
  ▼
Pipeline
  │
  ├── organizes ───────────────► Operator
  │                                 │
  │                                 │ executes with
  │                                 ▼
  │                              Context
  │                                 │
  │                                 ├── provides access to Event
  │                                 └── provides access to State
  │
  ├── declares ────────────────► Logical State
  │                                 ▲
  │                                 │
  │                        accessed by Operators
  │
  └── defines ─────────────────► Processing Topology
                                    │
                                    ├── Event Flow
                                    ├── Processing Dependencies
                                    └── State Access Relationships


Runtime
  │
  ├── executes ────────────────► Pipeline
  ├── invokes ─────────────────► Operator
  ├── provides ────────────────► Context
  └── manages ─────────────────► Physical State


Logical State
  │
  │ mapped by Runtime
  ▼
Physical State


Agent Operator
  │
  │ executes
  ▼
Agent


Plugin
  │
  │ extends
  ▼
Extension Points
```

## Event, State, and Context

### Event and State

Event and State are independent concepts.

An Event represents something that happened or a unit of data being processed by the system.

A State represents information maintained across processing operations.

Events may influence State through processing:

```text
Event
  │
  │ processed by
  ▼
Operator
  │
  │ reads / updates
  ▼
State
```

State may be created, updated, or derived from one or more Events.

For example:

```text
UserClicked
UserViewed
UserPurchased
        │
        ▼
user_10m_activity_count
```

State does not necessarily contain Events, and Events do not own State.

### Context

Context provides a processing-time view of information relevant to an operation.

Context does not own Event or State.

Instead, Context provides access to relevant information:

```text
Context
  │
  ├── Current Event
  ├── Relevant State
  ├── Processing Metadata
  └── Runtime Information
```

An Operator interacts with the processing environment through Context:

```text
Operator
   │
   │ executes with
   ▼
Context
   │
   ├── Event
   ├── State
   └── Other Relevant Information
```

Context is an access boundary rather than an ownership boundary.

---

## Operator and State

Operators perform processing operations within StreamMind.

An Operator may:

- Read Events
- Transform Events
- Enrich Events
- Filter Events
- Read State
- Update State
- Produce new Events
- Invoke AI models
- Invoke Agents
- Perform system operations

Operators explicitly declare their State dependencies.

For example:

```text
Feature Operator

requires:
- user_10m_activity
- user_profile
```

An Operator should not implicitly depend on hidden State.

State dependencies should be discoverable and explicit.

An Operator may depend on multiple States, and a State may be accessed by multiple Operators.

---

## Pipeline and Operator

A Pipeline defines a logical processing workflow.

A Pipeline organizes Operators and defines their relationships.

The Pipeline itself does not directly process Events. Processing is performed by Operators.

A Pipeline defines:

- Participating Operators
- Logical processing topology
- Processing dependencies
- State definitions
- State access relationships
- Logical processing constraints

A Pipeline may represent a linear flow:

```text
A → B → C
```

or a branching topology:

```text
       ┌── B ──┐
A ─────┤       ├── D
       └── C ──┘
```

The Pipeline defines logical processing relationships.

The Runtime determines how those relationships are physically executed.

---

## Pipeline and State

### Pipeline-visible State

State should be visible at the Pipeline level.

The Pipeline centrally declares logical State resources:

```text
Pipeline
│
├── Operators
│   ├── Operator A
│   ├── Operator B
│   └── Operator C
│
└── State Definitions
    ├── user_10m_activity
    ├── user_profile
    └── user_embedding_history
```

This avoids hiding all State inside individual Operator implementations.

Pipeline-level State declaration improves:

- Discoverability
- Dependency visibility
- State lifecycle management
- Shared State identification
- Pipeline-level auditing

The Pipeline acts as the logical management boundary for State.

### State Responsibilities

Responsibilities are divided across three concepts.

#### Operator

Declares:

> What State do I need?

#### Pipeline

Declares:

> What logical State exists in this workflow and how is it logically accessed?

#### Runtime

Determines:

> How is this State physically implemented and managed?

The relationship is:

```text
Operator
    declares State dependencies

Pipeline
    declares logical State
    and State access relationships

Runtime
    maps and manages
    physical State
```

---

## Shared State and State Access

A State may be accessed by multiple Operators.

The relationship between Operators and State is many-to-many.

```text
One State
    │
    └──► Multiple Operators

One Operator
    │
    └──► Multiple States
```

For example:

```text
State: user_10m_activity

used by:
- Business Logic Operator
- System Operator
- AI Operator
```

State sharing is allowed, but State access should be explicit.

State access may include:

- Read
- Write
- Read / Write

For example:

```text
State: user_10m_activity

Operator A → Read / Write
Operator B → Read
Operator C → Read
```

The exact access-control model remains an open design question.

The current principle is:

> State sharing is allowed, but State access should be explicitly declared.

---

## Pipeline Topology and State Consistency

Pipeline topology defines logical processing dependencies.

For example:

```text
Event
  │
  ▼
Operator A
  │
  │ updates State X
  ▼
Operator B
  │
  │ reads State X
  ▼
Operator C
```

This establishes a logical relationship:

```text
A happens before B
B happens before C
```

However, logical ordering does not imply globally single-threaded physical execution.

Events may still be processed concurrently.

Therefore, StreamMind distinguishes between:

### Logical Ordering

Defined by the Pipeline.

### Physical Consistency

Managed by the Runtime.

The Runtime is responsible for execution semantics including:

- Parallel execution
- Key partitioning
- State access
- Checkpointing
- Recovery
- Concurrent processing
- Failure handling

The relationship is:

```text
Pipeline
    │
    │ defines logical dependencies
    ▼
Runtime
    │
    │ preserves required execution semantics
    ▼
Physical Execution
```

---

## Logical State and Physical State

StreamMind distinguishes between logical State and physical State.

### Logical State

Logical State is the State abstraction visible in a StreamMind Pipeline.

For example:

```text
user_10m_activity
```

Logical State may define:

- Name
- Key
- Lifetime
- Visibility
- Access relationships
- Logical dependencies

### Physical State

Physical State is the implementation used by the Runtime and execution engine.

It may be implemented using:

- Flink Keyed State
- Flink Operator State
- External storage
- AI memory storage
- Other Runtime-managed storage

The relationship is:

```text
Pipeline
    │
    │ declares
    ▼
Logical State
    │
    │ mapped by Runtime
    ▼
Physical State
```

A logical shared State does not necessarily correspond to a single shared physical mutable object.

The Runtime determines the physical implementation based on:

- Access patterns
- Parallelism
- Partitioning
- Consistency requirements
- Execution engine capabilities

---

## State Scope

State scope may have multiple dimensions:

```text
State
│
├── Ownership
├── Key / Partition
├── Lifetime
└── Visibility
```

For example:

```text
State:
    user_10m_activity

Key:
    userId

Lifetime:
    10-minute window

Visibility:
    Pipeline Shared
```

Another example:

```text
State:
    agent_memory

Key:
    agentId

Lifetime:
    Persistent

Visibility:
    Agent-specific
```

Possible State scopes may include:

- Operator-local State
- Pipeline State
- Runtime State
- Agent State
- External Persistent State

The Pipeline is an important State management boundary, but it is not necessarily the only possible State scope.

---

## Pipeline and Runtime

Pipeline and Runtime have different responsibilities.

The Pipeline defines:

> What should happen?

The Runtime determines:

> How should it run?

### Pipeline

The Pipeline defines:

- Operators
- Processing topology
- Processing dependencies
- State definitions
- State access relationships
- Logical processing constraints

### Runtime

The Runtime is responsible for:

- Executing Pipelines
- Invoking Operators
- Providing Context
- Managing physical State
- Determining parallelism
- Determining partitioning
- Scheduling execution
- Managing resources
- Managing checkpointing
- Managing recovery
- Preserving execution semantics

The relationship is:

```text
Pipeline
    │
    │ defines processing intent
    ▼
Runtime
    │
    │ determines execution strategy
    ▼
Physical Execution
```

The same Pipeline may potentially result in different physical execution strategies depending on Runtime configuration and execution environment.

---

## Runtime and Context

Context is provided by the Runtime during processing.

```text
Runtime
   │
   │ provides
   ▼
Context
   │
   ▼
Operator
```

Context provides Operators with access to the information required during execution.

This may include:

- Current Event
- Relevant State
- Processing metadata
- Runtime metadata
- External information
- Enriched information

Operators should interact with the processing environment through Context rather than directly depending on Runtime internals.

## Agent and Operator

An Agent is integrated into StreamMind processing through an Agent Operator.

```text
Pipeline
    │
    ▼
Agent Operator
    │
    │ executes
    ▼
Agent
```

The Agent may consume Context and interact with State through StreamMind abstractions.

The Agent should not need to understand the complete Pipeline topology in which it is executed.

The Operator acts as the integration boundary between:

```text
StreamMind Processing
        │
        ▼
Agent Execution
```

## Plugin Relationships

A Plugin is an extension mechanism.

A Plugin is not necessarily part of the Event processing flow.

Instead:

```text
Plugin
   │
   │ extends
   ▼
Extension Point
```

Extension Points may exist in different parts of StreamMind, including:

- Operators
- Runtime
- State providers
- AI providers
- Agent capabilities
- Sources
- Sinks

Plugin is a cross-cutting extension concept.

The core processing model should not depend on a specific Plugin implementation.

## Mapping to Flink

StreamMind should not unnecessarily duplicate Flink's existing graph abstractions.

The current direction is:

```text
StreamMind Pipeline
        │
        │ build / compile
        ▼
Flink JobGraph
        │
        ▼
Flink ExecutionGraph
        │
        ▼
Flink Runtime
```

StreamMind provides higher-level abstractions such as:

- Operator definitions
- State definitions
- State access relationships
- Context model
- AI integration
- Agent integration

Flink provides execution-level capabilities such as:

- Dataflow relationships
- Operator topology
- Execution planning
- Parallel execution
- Partitioning
- Scheduling
- State execution semantics

StreamMind should extend the logical programming model where necessary rather than recreate Flink's execution model.

---

## Processing Graph Decision

A separate StreamMind Processing Graph was considered.

The proposed model was:

```text
Pipeline
    │
    ▼
Processing Graph
    │
    ▼
Execution Graph
    │
    ▼
Runtime
```

However, the current design does not demonstrate a clear requirement for a separate Processing Graph abstraction.

Most current requirements can be represented by:

- Pipeline definitions
- Pipeline metadata
- State definitions
- State access relationships
- Existing Flink graph abstractions

The fact that State becomes a Pipeline-visible logical resource does not, by itself, justify a new Graph abstraction.

Therefore, Processing Graph is not currently included as a Core Concept.

The current direction remains:

```text
StreamMind Pipeline
        │
        ▼
Pipeline Builder / Compiler
        │
        ▼
Flink JobGraph
        │
        ▼
Flink ExecutionGraph
        │
        ▼
Flink Runtime
```

A separate Processing Graph may be reconsidered if StreamMind introduces semantics that cannot be directly mapped to Flink topology.

Possible examples include:

- Automatic expansion of AI Operators
- State coordination nodes
- Complex asynchronous AI workflows
- Generated retry or compensation flows
- Agent orchestration graphs
- Other logical execution constructs that require transformation before becoming Flink operators

The design principle is:

> Do not introduce an abstraction until there is a clear problem that requires it.

## Core Design Principles

The current relationship model follows these principles:

1. Event and State are independent concepts.
2. Context provides processing-time access to relevant information without owning that information.
3. Operators perform processing and explicitly declare their dependencies.
4. Pipelines define logical processing workflows rather than performing processing themselves.
5. State is a Pipeline-visible logical resource.
6. Operators declare State dependencies, while Pipelines centrally declare logical State definitions.
7. A State may be shared by multiple Operators.
8. State access should be explicit rather than implicitly hidden inside Operators.
9. Pipeline topology defines logical processing dependencies and ordering constraints.
10. Pipeline topology alone does not solve all physical State consistency problems.
11. Runtime is responsible for physical execution, concurrency, checkpointing, recovery, and State consistency semantics.
12. Logical State and Physical State should be separated.
13. A logical shared State does not necessarily correspond to a shared physical mutable State object.
14. The Pipeline defines what should happen; the Runtime determines how it runs.
15. Agents integrate with stream processing through Operators.
16. Plugins extend StreamMind through explicit extension points.
17. StreamMind should reuse and extend Flink abstractions where possible rather than recreate existing execution concepts.
18. New abstractions should only be introduced when they solve a clearly identified problem.

---

## Current Core Concepts

The current StreamMind Core Concepts are:

- Event
- State
- Context
- Operator
- Pipeline
- Runtime
- Plugin
- Agent

Processing Graph is not currently a Core Concept.

It remains a possible future abstraction if StreamMind develops processing semantics that require a logical graph layer beyond the Pipeline model and the underlying Flink graph.
